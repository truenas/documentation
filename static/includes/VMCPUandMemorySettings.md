{{< truetable >}}
| Setting | Description |
|---------|-------------|
| **Virtual CPUs** | Text entry field to manually enter the number of virtual CPUs to allocate to the virtual machine. The VM operating system might have operational or licensing restrictions on the number of CPUs. Consult the documentation and requirements for the planned operating system configured for this VM. TrueNAS enforces a maximum of 255 total virtual CPUs per VM (**Virtual CPUs** multiplied by **Cores** multiplied by **Threads**). The VM fails to save if the total exceeds this maximum. |
| **Cores** | Text entry field to manually enter the number of cores per virtual CPU socket. |
| **Threads** | Text entry field to manually enter the number of threads per core. |
| **Optional: CPU Set (Example: 0-3,8-11)** | Text entry field to manually enter the logical cores this VM can use. Better cache locality can be achieved by setting the CPU set based on the CPU topology (e.g., to assign cores 0, 1, 2, 5, 9, 10, and 11, you can enter 1-2,5,9-11). This field's label includes **Optional**, but TrueNAS requires a value here when **Pin vcpus** is selected. |
| **Pin vcpus** | Requires a value in **CPU Set**. Pins each virtual CPU to one of the host CPU cores listed in **CPU Set**, in the order the cores appear there. The number of cores listed in **CPU Set** must equal the total number of virtual CPUs (**Virtual CPUs** multiplied by **Cores** multiplied by **Threads**), or the VM fails to save. Pinning improves CPU cache locality and can reduce stutter in GPU passthrough VMs. |
| **CPU Mode** | Sets the CPU virtualization mode to the option selected on the dropdown list. **Custom** is the default. Options are:<ul><li>**Custom** - Emulates a specific CPU model selected in **CPU Model**. The guest sees the same CPU features regardless of which physical system runs the VM, keeping VM behavior predictable across a hardware upgrade or a restore to a different TrueNAS system.</li><li>**Host Model** - Emulates a CPU model that closely matches the host CPU, then adds compatible host CPU features on top of that model. This gives near-native performance without exposing every low-level detail of the host CPU to the guest. Host Model trades some of the predictability of Custom for performance closer to Host Passthrough.</li><li>**Host Passthrough** - Passes the host CPU directly to the guest with no emulation layer, for the best possible performance and full access to host CPU features. Restoring this VM on different hardware might fail or change VM behavior, since the guest CPU no longer matches the new host exactly.</li></ul>Only select **Host Model** or **Host Passthrough** when this VM has CPU-intensive requirements that justify that tradeoff. **Custom** also shows the **CPU Model** setting. |
| **CPU Model** | Sets the CPU model to the option selected on the dropdown list. |
| **Memory Size** | Text entry field to manually enter the amount of RAM allocated for the VM. The minimum value is **256 MiB**. |
| **Minimum Memory Size** | Text entry field to manually enter the minimum amount of memory. When not specified, a guest system is given a fixed amount of memory specified above. When specified, a guest system is given memory within the range between the minimum and fixed as needed.  |
| **Optional: NUMA nodeset (Example: 0-1)** | Text entry field to manually enter the node sets. The node set allows setting NUMA nodes for multi-NUMA processors when the CPU set is defined. Better memory locality can be achieved by setting the node set based on the assigned CPU set (e.g., if CPUs is 0, and 1 belongs to NUMA node 0, then setting nodeset to 0 improves memory locality). |
